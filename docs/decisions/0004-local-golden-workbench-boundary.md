# 0004：本地 Golden Workbench 边界

状态：Accepted
日期：2026-08-21

## 背景

M1 需要对 12 个代表页面进行人工标注。直接编辑 JSON 无法可靠检查坐标、阅读顺序和模型
建议，也容易把 MinerU 输出误当成真值。完整 Tauri Studio 尚未进入 M5，当前不应提前引入
桌面运行时或通用 Agent 编排框架。

## 决策

建立一个面向 M1 的轻量本地工作台：

- React/Vite 前端位于独立 `studio/`，不把 Node 依赖加入 Python Core；
- Python 标准库 HTTP 服务只暴露当前 golden dataset、页面 artifact 和解析预测；
- MinerU 预测始终是只读建议层，人工接受后生成 `draft` 真值并记录结构化建议来源；
- 保存以 dataset 内容哈希作为乐观并发修订号，冲突时拒绝覆盖；
- 文件写入采用同目录临时文件和原子替换；
- 前端构建产物属于本地运行产物，不进入版本控制。

工作台不会定义未来的 Workflow IR，也不依赖 LangGraph。完整 Tauri 应用可复用这里验证过的
标注数据模型和交互，但不受当前 HTTP 托管方式约束。

## 后果

人工标注可以在真实页面上完成，模型建议与真值的边界可审计。Core 只增加小型工作区服务，
前端框架不会扩散到解析和评测模块。开发者需要分别锁定 uv 与 npm 环境，并在运行工作台前
构建前端。

## 未选择的方案

- 直接采用 Dify：它面向通用 LLM 工作流，无法提供数学页面坐标标注所需的专用交互；
- 现在封装 Tauri：标注模型尚未经过真实使用验证，桌面封装会增加无关复杂度；
- 让浏览器直接修改本地文件：权限和并发行为不可控，无法可靠执行原子保存与 Schema 校验。
